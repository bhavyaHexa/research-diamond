# Proposed folder structure: React + TypeScript, React Three Fiber, MobX

Written for: the developer restructuring this viewer. This is a plan. Nothing here has been created yet.

Current state is described in [ARCHITECTURE.md](ARCHITECTURE.md).

This version is leaner than the first draft. Each file groups one topic, and the MobX store holds the get and set logic instead of separate apply files.

## 2. Which files are actually needed

Some files in the first draft were split for no good reason. Here is what happened to each.

| First draft | Now | Why |
| --- | --- | --- |
| `engine/loadEngine.ts`, `engine/createViewer.ts`, `engine/viewerController.ts`, `scene/useViewer.ts` | `engine.ts` | One import, one create, one dispose. Four files for that is overhead. |
| `scene/camera/cameraConfig.ts`, `cameraIntro.ts`, `cameraFraming.ts` | `scene/camera.ts` | The config values are used only by the intro code. |
| `scene/lights/*` (three files) | `scene/lights.ts` | Three small loaders; one file is easier to read. |
| `scene/ground/ground.ts`, `scene/render/renderConfig.ts`, `lightsConfig.ts` | `scene/setup.ts` | Each is a few lines of settings. They all run once at setup. |
| `scene/ring/loadRing.ts`, `loadScenePreset.ts` | `scene/ring.ts` | Both load the ring's scene. |
| `scene/materials/` (four files) | `scene/materials.ts` | Config, whitening, and apply all work on the same materials. |
| `store/` (five files) | `store.ts` | Each store is about 10 lines. `CameraStore` is dropped: the intro state fits in `ViewerStore`. |
| `auth/hash.ts`, `auth/session.ts` | `auth.ts` | Both are about 20 lines. |
| `components/OptionsPanel/` (three files) | `components/OptionsPanel.tsx` | The tiles are small components inside one file. |
| `components/AuthGate/` (two files) | `components/AuthGate.tsx` | The form is part of the gate. |
| `styles/` (three files) | `index.css` | One stylesheet is enough for this page. |
| `lib/slug.ts` | `utils.ts` | Shared helpers go in one utils file. |

**Things that must stay as separate files:**
- `constants.ts`: you asked for one file of fixed paths.
- `vendor.d.ts`: TypeScript needs it for the minified engine.
- `auth.config.ts`: generated and gitignored, so it has to be its own file.
- `main.tsx` and `App.tsx`: the entry points.

## 3. Get and set logic lives in the store

MobX gives you getters and setters for free, so the separate apply files are not needed. The store's actions do the work:

```ts
// store.ts
class MaterialStore {
  metal: MetalKey = DEFAULT_METAL;
  gem: GemKey = DEFAULT_GEM;

  constructor() {
    makeAutoObservable(this);
    reaction(() => this.metal, (key) => applyMetal(key));
    reaction(() => this.gem, (key) => applyGem(key));
  }

  setMetal(key: MetalKey) { this.metal = key; }
  setGem(key: GemKey) { this.gem = key; }
}
```

- The UI calls `materials.setGem("white")`. It never touches the engine.
- The `reaction` calls `applyGem` in `scene/materials.ts`, which writes the values to the diamond materials.
- `scene/materials.ts` holds the functions that touch engine objects. Those stay outside MobX on purpose: MobX must not wrap Three.js meshes or materials, because that slows the render loop.

## 4. Fixed paths in one file

`src/constants.ts` is the only place a URL or file path is written:

```ts
export const PATHS = {
  ring: "/assets/Ring_v1.glb",
  scenePreset: "/assets/scene/designer-scene.vjson",
  gemEnvironment: "/assets/scene/gem-000.hdr",
  lightmap: "/assets/scene/lightmap-r-2b.hdr",
  vendorBundle: "/vendor/engine-0.8.0/bundle-0.8.0.mjs",
  authConfig: "./auth.config",
} as const;
```

Tuning values (zoom limits, quality, material numbers) stay in their scene file, for example `ZOOM` at the top of `scene/camera.ts`.

## 7. React Three Fiber: the open decision

This still decides the design, so it needs an answer before building.

The engine (`ViewerApp`, `addBasePlugins`, `DiamondPlugin`, the GLB's `WEBGI_viewer` settings) creates its own renderer on a canvas you give it. R3F's `<Canvas>` also creates a renderer and owns its canvas. Two renderers cannot cleanly share one WebGL context, and the engine is not a three.js scene that R3F can host.

1. **Recommended:** R3F creates the canvas and `ViewerCanvas.tsx` passes `gl.domElement` to the engine. R3F's loop is turned off (`frameloop="never"`), so the engine does the drawing. This keeps the diamond shader and the GLB settings. It is untested, so start with a short spike.
2. **Full rewrite:** replace the engine with three.js + R3F + drei. This is the cleanest React design and the most work. The diamond look, scene presets and post-processing would all be rebuilt by hand.

Tell me which option you want.

## 8. Build and deploy impact

- Vite means the site needs a build. The workflow must sync `dist/`, not `.`. The exclusion for `auth/build-auth.mjs` moves to `scripts/`.
- `auth.config.ts` is generated before the build. Its hash is public, as now; the secret is never shipped.
- The vendor bundle stays a static file loaded by dynamic import, so the engine stays out of the main bundle.
- `public/assets` keeps the same URLs, so the scene files do not change.
